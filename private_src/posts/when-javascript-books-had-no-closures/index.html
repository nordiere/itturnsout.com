When JavaScript (books) had no closures

published 2015-10-22

JavaScript is a survivor among web technologies. Turned 20 and still as relevant as ever.

Over that time the way in which we use it has changed greatly, from tiny scripts that changed images on mouseover, to huge web apps that replaced most of the offline applications we once used.

This evolution took place even for aspects of the language which have not changed at all. A great way to see this is by comparing how "JavaScript: The Definitive Guide" wrote about closures over the years.

"JavaScript: The Definitive Guide"

David Flanagan's "JavaScript: The Definitive Guide" is a rare example of an in-print JavaScript book that is almost as old as JavaScript itself. It has been in print non-stop for almost 20 years, getting updated every few years.

It is one of the most influential JavaScript books ever, and was especially invaluable in the days before Google and StackOverflow. Netscape's Rhino engine got its name from The Definitive Guide's cover animal, not the other way around.

Closures

Closures are an integral and immutable part of JavaScript. They have been there from the start, they have never changed, and they will never change.

This is an important distinction. Of course the older editions of the book do not cover features introduced in EcmaScript 5, and the newer ones do not need to devote an entire section to "Arrays in [Netscape] Navigator 2.0". But closures have been the same since day one. This makes them an excellent candidate for a chronological comparison.

This comparison doesn't show how the language changed. It shows how our use of the language changed.

Closures in The Definitive Guide

With help from Toronto Public Library, I put together a timeline of coverage of closures in various editions of Mr. Flanagan's book:

1997Not one word.
2002Two sentences mentioning closures, practically as an aside.
2006A large section, shared with function scope. It contains extensive examples of closures.
2011A large section, dedicated to closures alone. Many other parts of the book demonstrate programming techniques that make use of closures, referencing back to this section.

What this shows

While closures never changed, their relevance did.

This is a direct consequence of the change in the way in which we use JavaScript. If all you are doing is running a simple onclick script, you will not run into closures. To run into closures, you need to have a function create and return another function. This is a useful, but advanced programming technique. That's why questions about closures are popular in job interviews. They are a good proxy for "Have you programmed a large web app in JavaScript?"

The book's coverage of closures reflects the way our use of JavaScript has evolved:

  • In 1997 nobody programmed large JavaScript web apps.

  • In 2002 only a handful did. (I think Outlook Web Access for Internet Explorer 5, released in 1999 along with the necessary XMLHttpRequest technology, may have been the first true "Web 2.0" app.)

  • By 2006 early frameworks like Dojo and Prototype have become popular, and jQuery was soon to follow. The use of JavaScript was exploding.

  • By 2011, everyone knew jQuery, and most JavaScript programming involved large web apps. Modern JavaScript MVC frameworks were arising, and closures were routinely used to provide encapsulation and other techniques that make large apps manageable.

I hope Mr. Flanagan is working on the next edition. Although I think his coverage of closures is already maxed out.
